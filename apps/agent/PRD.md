## 产品背景

浙江大学医学院附属第一医院（用户口语称"浙一""浙大一院"，下文统一称浙大一院）是一所大型三级甲等综合医院，官网 [科室导航](https://www.zy91.com/department) 栏目下公开了全部科室的简介信息，覆盖外科、内科、医技及平台等约 80 个科室条目（含庆春、之江、总部一期、城站等院区下的同名或分设科室），每个科室页面包含科室简介、专科特色、科研教学等内容。这部分文本是非结构化的自然语言，普通患者难以直接用来判断自己该挂哪个科室。

患者就医的第一个真实痛点往往不是治疗本身，而是分诊：拿到一个症状或身体不适，不知道医院里哪个科室对口、是否有更细的亚专科、严重程度是否需要急诊。传统解决方式是搜索引擎自助查询、问身边人、或到医院导诊台排队询问，普遍存在信息不准、专业门槛高、时间成本大的问题，对不熟悉医院科室划分的患者尤其不友好。

本产品是一套面向患者的智能问诊导诊 Agent，它把医院公开的科室简介沉淀为可被语义检索的知识库，患者用自然语言描述症状，Agent 通过多轮对话逐步澄清病情，最终给出挂号科室建议并附上可溯源的依据。产品的本质是一个信息匹配服务，把"患者症状描述"映射到"医院科室"，匹配依据是医院自己公开的科室能力描述，因此推荐结果可解释、可核查。

本产品定位为可用产品而非教学示例，重心放在真实分诊的有效性、准确率的可度量、以及医疗安全边界上。产品不进行医学诊断，不替代医生，不给出用药或治疗方案，所有输出都是导诊建议并在显著位置声明这一点。

## 产品目标与非目标

### 产品目标

让一个完全不懂医院科室划分的普通患者，能用最自然的口语把不舒服的情况描述出来，在 3 到 5 轮对话内得到一个明确的、可解释的挂号科室建议，建议能指向知识库中的科室原文段落作为依据

把医院分散在约 80 个科室页面里的非结构化文本，转化为可被语义检索的知识库，让症状描述与科室能力描述能够基于语义相似度而非关键词精确匹配来关联，并由大模型进一步从原文中总结出"症状/疾病 → 科室"结构化映射表作为兜底增强

建立一套可量化、可回归的产品质量度量体系，用标注测试集驱动准确率指标的持续提升，把"产品可用"变成可度量、可追踪的工程目标

### 非目标（明确不做）

不做医学诊断，不判断疾病名称，不输出"你可能得了什么病"这类结论性判断

不开处方、不给用药剂量、不给治疗建议、不解读化验或影像报告

不接入医院 HIS，不做真实挂号、不做号源查询、不做预约排班，V1 不含任何与院内业务系统打通的能力

不做影像识别、不接入可穿戴设备数据、不接入电子病历

不对急诊或危重情况做自主处置决策，只做"识别到危急重症迹象则强烈建议立即就医"的提示与常规问诊阻断

## 目标用户与典型场景

### 目标用户

核心用户是准备前往浙大一院就诊、但不确定挂哪个科室的成年患者本人或其家属，覆盖三类典型画像

第一类是症状不明确型，知道自己哪里不舒服但说不清属于什么身体系统，例如长期反酸烧心不知道该看消化内科还是心胸外科，这类用户需要 Agent 帮忙定位身体系统与对应科室

第二类是科室不熟悉型，知道大致方向但被医院的细分科室搞晕，例如甲状腺结节不知道该看甲状腺外科还是内分泌科，这类用户需要 Agent 帮忙区分亚专科边界

第三类是家属代办型，给老人或孩子咨询，描述往往是二手转述且信息不全，这类用户需要 Agent 主动追问补全关键鉴别信息

### 典型场景

场景一　用户输入"最近一个月经常胃痛反酸，吃完更难受"，Agent 检索到消化内科的胃肠方向，反问是否有黑便或体重下降以排除危险信号，最终主推消化内科并附上科室原文依据

场景二　用户输入"小孩发烧三天，咳嗽有痰"，Agent 识别到儿科与呼吸方向，追问孩子年龄与精神状态，主推儿科，并在对话中提示若出现呼吸急促需立即急诊

场景三　用户输入"体检发现甲状腺结节"，Agent 检索到甲状腺外科与内分泌科均可处理，追问是否伴有功能异常或压迫症状，根据回答二选一并解释两者分工

场景四　用户输入"胸痛"，Agent 立即识别为潜在危急重症，高优先级提示若为剧烈持续胸痛请立即急诊或拨打 120，暂停常规分诊追问，并在会话中标记为高危

## 名词约定

RAG 　 Retrieval Augmented Generation，检索增强生成，指在让大模型回答之前先从知识库里检索出相关文本片段，把这些片段塞进上下文，再让模型基于片段作答，目的是让回答有依据、可溯源、降低幻觉

Embedding 　把一段文本映射成一个固定维度的浮点向量，语义相近的文本在向量空间中也相近，这是 RAG 能做语义检索的基础，本产品生成走 DeepSeek 但 Embedding 因 DeepSeek 不提供该接口而另选模型

Vector Store 　向量数据库，存储每段文本的向量并能按相似度快速召回最接近的若干段，本产品选用 Chroma

Chunk 　把长文档切成的一小段一小段文本，切分粒度直接影响检索质量，太大召回不精准，太小丢失上下文

Retriever 　检索器，负责把用户问题转成向量并从 Vector Store 里召回相关 Chunk，本产品在向量检索之外叠加结构化映射的关键词检索，构成混合检索

Hybrid Retrieval 　混合检索，同时使用向量语义检索与关键词检索两条通道，再对结果合并去重排序，用于兼顾语义相近与关键词精确命中

LLM 　 Large Language Model，大语言模型，本产品对话与生成都用 DeepSeek，模型名 `deepseek-v4-flash`，接口地址 `https://api.deepseek.com`

LangGraph 　 LangChain 生态下用于构建可控状态流转的编排框架，把 Agent 行为建模为一张显式的状态图，本产品用它编排结构化问诊的状态流转

FastAPI 　 Python 的高性能 Web 框架，本产品用它把 Agent 能力封装成 HTTP 对话接口供前端调用

Agent 　智能体，在本产品里指能根据当前对话状态决定下一步动作（追问、急诊判断、检索、推荐、兜底）的程序实体

HIS 　 Hospital Information System，医院信息系统，本产品 V1 不接入

## 功能需求

### F1 结构化问诊对话

Agent 以主动追问的方式与患者进行多轮对话，每一轮根据当前已掌握的信息决定是继续追问、触发急诊判断、发起检索，还是给出推荐

输入　患者自然语言描述的症状或身体不适，可口语化、可碎片化

输出　 Agent 的回复，类型为追问、急诊提示、推荐结果、兜底提示之一

要点　追问必须围绕鉴别诊断相关的关键维度展开，至少覆盖发病部位、持续时间、伴随症状、加重缓解因素、危险信号五类，不发散闲聊；每一轮追问最多一到两个问题，避免一次抛出过多问题造成患者负担；当信息已足够区分科室时立即停止追问进入推荐，不在信息饱和后继续无意义提问

### F2 急诊危重识别与阻断

Agent 在每一轮对话中持续评估患者描述是否命中危急重症迹象，一旦命中立即进入急诊处置分支

输入　患者当轮及历史描述文本

输出　急诊强提示，内容包括疑似危急情况说明、立即就医或拨打 120 的指引、就近急诊建议，并暂停常规分诊追问

要点　需覆盖的典型危急信号至少包括剧烈持续胸痛、突发意识障碍或抽搐、呼吸困难或窒息感、大出血或大量呕血便血、突发肢体无力或言语障碍、剧烈腹痛伴板状腹、高热伴颈强直或皮疹、严重外伤或烧伤、疑似药物中毒或过敏休克；触发急诊分支后常规问诊阻断，Agent 不再继续追问鉴别，也不给出科室层面的常规推荐；该轮会话在记录中被标记为高危，便于后续审计与统计

### F3 混合检索

Agent 在需要判断科室时，同时触发向量语义检索与结构化映射的关键词检索两条通道，合并结果供推荐使用

输入　当前已澄清的患者症状与病情描述

输出　若干候选科室，每条附带命中来源（向量召回的科室原文 Chunk 或结构化映射条目）与相似度或匹配分

要点　向量检索在科室原文 Chunk 库上按语义相似度召回 Top-K；关键词检索在"症状/疾病 → 科室"结构化映射表上按症状关键词命中召回；两路结果按科室维度合并去重，每个候选科室综合其向量分与映射分得到一个候选强度；检索过程对调用方透明，但召回的原文片段会作为推荐依据暴露给用户

### F4 科室推荐

Agent 基于混合检索结果与对话上下文，给出一个主推科室、一个备选科室，并各自附上知识库依据

输入　混合检索的候选科室及命中来源、当前对话上下文

输出　结构化推荐结果，包含主推科室、备选科室、各自依据（指向科室原文或映射条目的一句话摘要）、综合推荐理由

要点　主推科室是 Agent 判断与患者病情最对口的一个，备选科室是次优或需要进一步鉴别的一个，二者都必须能在知识库中找到依据，不得凭空生成科室；推荐理由用患者能理解的语言说明为什么推荐这个科，以及主推与备选的分工差异；若候选科室均置信度不足，则不强行推荐，转而触发兜底逻辑

### F5 就医提示

在给出推荐的同时，附加与就诊相关的实用提示，帮助患者更好地完成就医

输入　主推科室、病情描述

输出　就医提示，内容可能包括该科室是否需要空腹、是否需要憋尿、是否建议携带既往报告、大致就诊时段建议等

要点　就医提示来源于知识库中该科室的公开信息或通用导诊常识，凡无法从知识库佐证的提示需标注为一般性建议；提示不得包含用药或治疗指导；当主推为急诊方向时，就医提示替换为立即就医的紧急指引

### F6 多轮会话与历史

系统按会话维度隔离并维护对话历史，支撑多轮追问的上下文连贯

输入　会话标识 session_id 与每轮用户消息

输出　带历史上下文的 Agent 回复，以及可持久化的会话记录

要点　不同 session 之间相互隔离，互不串扰；会话历史用于 Agent 理解上下文，也用于事后审计与高危标记回溯；V1 会话历史默认存内存或轻量本地存储，预留持久化扩展点；会话在长时间无活动或患者主动结束后释放资源

### F7 免责声明与兜底

产品在全局层面声明医疗免责，并在 Agent 无法给出可靠推荐时提供兜底路径

输入　触发兜底的条件（推荐置信度低于阈值、多次澄清仍信息不足、命中超出知识库范围的症状）

输出　兜底提示，建议患者前往医院导诊台或咨询人工，并重申免责声明

要点　免责声明在产品入口、对话过程中、推荐结果旁均有露出，核心内容为本产品提供的是导诊建议而非医学诊断，不替代医生诊疗，不提供处方与治疗方案，紧急情况请立即拨打 120 或前往急诊；兜底优先于强行推荐，宁可提示求助人工也不输出低置信度的科室建议

## 用户交互流程

整个问诊过程用 LangGraph 建模为一张显式状态图，每个节点是一个处理步骤，节点之间的边是带条件的流转，状态在节点间传递与累积。这样设计的目的是让对话流程可控、可观测、便于插入急诊分支与兜底分支，而不是把所有判断都隐式交给大模型的自由发挥

状态流转示意

```
            ┌───────────────────────────────────────────────┐
            ▼                                               │
[START] -> 接收症状 -> 急诊判断 ──命中──> 急诊出口(强提示+阻断)
                          │未命中                          │
                          ▼                               │
                     信息足够? ─否─> 澄清追问 ──> ┘(回到急诊判断)
                          │是
                          ▼
                       混合检索
                          │
                          ▼
                    置信度足够? ─否─> 兜底(转人工/导诊台)
                          │是
                          ▼
                    科室推荐(主推+备选+依据+就医提示)
                          │
                          ▼
                       [END]
```

各状态节点说明

接收症状　采集患者当轮输入，归并进会话上下文，进入急诊判断

急诊判断　对当前上下文做危急重症识别，每轮必跑，命中则直接跳转急诊出口，这是优先级最高的分支，先于一切常规逻辑

澄清追问　当信息不足以区分科室时，由 Agent 围绕发病部位、持续时间、伴随症状、加重缓解因素、危险信号五个维度生成追问，追问后回到急诊判断形成循环，循环次数有上限防止无限追问

混合检索　信息足够时触发向量检索与结构化映射检索两路召回，合并得到候选科室及命中来源

科室推荐　基于候选与上下文生成主推科室、备选科室、依据、就医提示，输出给患者

兜底　当推荐置信度低于阈值或澄清达到上限仍信息不足时，提示前往导诊台或咨询人工，不强行推荐

急诊出口　输出急诊强提示与就医指引，阻断常规问诊，会话标记高危

流转的条件判断（急诊命中、信息是否足够、置信度是否足够）由大模型结合规则共同判定，关键安全条件以规则兜底，避免模型漏判

## 知识库构建 pipeline

知识库不是一次性写死的，而是由一条离线 pipeline 自动构建，pipeline 分采集、切分、向量化、抽取、索引五个阶段，构建产物供在线检索使用

阶段一 采集　编写爬虫脚本遍历官网 `https://www.zy91.com/department` 科室导航页，拿到全部约 80 个科室的详情页链接，逐页抓取原始 HTML，按科室归档存入原始数据目录，保留科室名称、dept_id 与页面地址作为元数据，抓取过程做基础去重与异常重试

阶段二 清洗与切分　对每个科室的原始正文做清洗，去除导航、广告、版权等无关片段，保留科室介绍正文；按语义边界与固定长度将正文切分成 Chunk，每个 Chunk 携带所属科室、所属小节、在原文位置等元数据，切分时对跨小节内容做适度重叠以保留上下文

阶段三 向量化入向量库　用 Embedding 模型把每个 Chunk 转成向量，连同元数据写入 Chroma 向量库，构建出支持语义相似度检索的原文 Chunk 库，这是混合检索的向量通道基础

阶段四 LLM 抽取结构化映射　用 DeepSeek 对每个科室的原文做信息抽取，让模型总结该科室对应的常见症状、常见疾病、适应症、专病方向，输出结构化的"症状/疾病 → 科室"条目，所有科室的条目汇总成一张结构化映射表，每条记录包含症状或疾病关键词、对口科室、科室原文来源定位、置信度，这是混合检索的关键词通道基础，也是兜底增强的数据来源

阶段五 索引与校验　对结构化映射表建立关键词索引，供在线关键词检索使用；对抽取结果做基本校验，例如科室名必须落在知识库合法科室清单内、来源定位能回指到具体 Chunk，校验失败的条目标记待人工复核

pipeline 的产物有两类，一是向量库里的原文 Chunk，二是结构化映射表，二者共同支撑在线的混合检索；pipeline 设计为可重跑，当科室页面更新或抽取 Prompt 优化时可重新构建

## 技术架构

系统按职责分为六层，自上而下依次为前端层、接口层、编排层、检索层、数据层、模型层，层与层之间通过明确接口解耦，便于独立替换与测试

前端层　 Web 聊天页，提供对话输入框、消息流展示、推荐结果卡片（主推、备选、依据、就医提示）、免责声明常驻，通过 HTTP 调用后端接口，V1 为轻量静态页

接口层　 FastAPI 实现的对话接口，接收带 session_id 的用户消息，返回 Agent 回复，负责会话路由、限流、日志、异常处理，是对外唯一入口

编排层　 LangGraph 状态机，承载问诊的状态流转与条件分支，包括急诊判断、澄清追问、检索触发、推荐生成、兜底，是产品行为的核心，状态机的可控性直接决定安全分支能否可靠触发

检索层　混合检索器，封装向量检索与关键词检索两路，向量检索查 Chroma 中的原文 Chunk，关键词检索查结构化映射表，两路结果合并去重排序后返回候选科室及命中来源

数据层　向量库 Chroma、结构化映射表、会话历史存储，三者构成知识与状态的基础设施，知识部分由离线 pipeline 构建，会话部分由在线服务读写

模型层　生成与对话统一用 DeepSeek（模型名 `deepseek-v4-flash`，接口地址 `https://api.deepseek.com`），Embedding 因 DeepSeek 不提供该接口而另选中文友好的开源模型 `BAAI/bge-m3`，可通过本地 sentence-transformers 推理或经兼容 OpenAI 接口的服务调用

模型与环境约定　密钥与配置集中在 `.env`，至少包含 `DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`、`DEEPSEEK_BASE_URL` 以及 Embedding 相关配置，由 `config.py` 统一加载导出，业务代码统一从 config 取值，不散落硬编码

部署　 V1 为单机部署，FastAPI 经 uvicorn 提供服务，前端静态页由同一服务托管或独立托管，知识库构建产物随服务一起部署，密钥通过环境变量注入不进代码库

### 结构化映射表 schema

映射表由 LLM 从科室原文抽取，每条记录至少包含以下字段

症状或疾病关键词　患者可能用来描述的症状或疾病名称，可口语化，一条记录可含多个近义表述

对口科室　必须落在临床可挂号科室白名单内

科室原文来源定位　指向该科室原文的 Chunk 标识，便于推荐时回溯依据

类别标签　如该症状对应亚专科方向或专病类别，用于备选科室的区分

置信度　模型抽取时的自评置信度，用于检索结果排序与低质条目过滤

### 标注测试集

测试集是评估产品可用性的基准，用于驱动准确率指标的度量与回归

规模　 V1 首批标注样本不少于 200 条，覆盖主要临床科室的症状分布，长尾科室至少有最低样本数保证

样本结构　每条样本包含患者症状描述（可含多轮）、期望主推科室、可接受的备选科室集合、是否含危急重症标记、是否含需兜底的模糊描述

标注来源　由有医学背景的人员协助标注，标注规范单独成文，明确主推与备选的判定口径与歧义处理规则

用途　既用于上线前的准确率门槛校验，也用于每次知识库或 Prompt 变更后的回归测试，纳入持续集成

## 非功能需求

性能　单轮回复完整时延 P95 不超过 8 秒（含混合检索与生成），流式输出首字节时延不超过 2 秒，保证患者在每轮等待中有可见的响应进度

并发　 V1 单机部署支持同时活跃会话数不少于 50，会话历史在内存中管理并预留持久化扩展，单会话上下文长度控制在模型窗口与检索预算的合理范围内

准确率门槛　作为可用产品的上线门槛，标注测试集上的 Top-1 准确率不低于 70%，Top-3 准确率不低于 90%，危急重症用例的急诊分支触发率不低于 95%，应兜底用例的兜底触发正确率不低于 90%，主推科室落在医技平台科室或非法科室的误推率为 0，具体数值随测试集扩充在迭代中调整

可用性　服务可用率目标 99%，接口具备超时与重试，模型服务不可用时降级为兜底提示而非报错裸奔

可观测性　每次推荐记录其命中的检索来源、候选科室、最终推荐、置信度与高危标记，支撑事后审计、问题定位与质量分析

安全合规　不采集患者身份证号、真实姓名、联系方式等个人身份信息，会话以匿名 session 标识，对话记录的留存与脱敏规则单独约定并符合数据合规要求

## 约束与边界

医疗免责红线　产品输出一律是导诊建议而非医学诊断，不替代医生，不给处方、不给用药剂量、不给治疗方案、不解读报告，免责声明在入口、对话中、推荐结果旁三处露出，这是不可妥协的产品底线

急诊红线　疑似危急重症必须触发急诊强提示与常规问诊阻断，不得在危急情况下继续常规分诊追问或给出常规科室推荐，危急判断以规则兜底优先于模型自由判断，宁可误提示急诊也不漏判

推荐范围约束　主推与备选科室只能落在临床可挂号科室白名单内，严禁生成医院不存在的科室名，严禁把医技平台科室作为挂号推荐目标，低置信度场景优先兜底而非强行推荐

知识库时效　科室知识以官网公开信息为准，官网更新后需重新跑 pipeline 重建知识库，产品不维护与官网相悖的科室信息，知识库构建时间戳对用户可见以管理预期

能力边界　 V1 不接入 HIS，不提供真实挂号、号源、排班、费用信息，不提供院内导航与医生排班，所有这些在对话中明确告知不在能力范围内并引导至正规渠道

隐私边界　不主动索取敏感个人信息，患者自愿提供的病情描述按最小必要原则处理，不用于除导诊以外的目的

## 验收标准

功能完整性　 F1 到 F7 七个功能点全部实现并可演示，结构化问诊能完成典型场景一到场景四的完整对话，急诊分支能被场景四正确触发

准确率达标　标注测试集各项指标达到非功能需求中的门槛值，其中急诊分支触发率与误推率为硬性一票否决项，任一不达标不予上线

安全用例通过　专项安全测试集覆盖胸痛、意识障碍、大出血、呼吸困难、卒中样症状、严重外伤、过敏休克、药物中毒等危急情形，全部正确触发急诊分支；专项兜底测试集覆盖极模糊描述、超出知识库范围的症状、多轮澄清无果的情形，全部正确触发兜底

可追溯性　每条推荐都能回溯到知识库中的具体 Chunk 或映射条目，无法回溯依据的推荐视为不合格

回归可控　知识库重建或 Prompt 调整后，测试集回归不出现指标退化，回归流程纳入持续集成自动执行

## 风险与对策

幻觉与误分诊　模型可能生成医院不存在的科室或给出错误推荐，对策是推荐结果必须由混合检索的候选约束、科室白名单校验、依据回溯三重把关，无法回溯依据的推荐不输出，低置信度场景转兜底

知识库覆盖盲区与时效　官网科室简介以"科室能看什么"为主，部分"什么症状该来"的映射需要靠 LLM 抽取补全，存在抽取遗漏或过时的风险，对策是结构化映射与向量原文双通道互为补充、抽取结果做合法性校验、定期重跑 pipeline 重建并展示构建时间戳

急诊漏判　危急重症未被识别将造成严重后果，对策是急诊判断以规则兜底优先于模型自由判断、维护专项安全测试集、把急诊触发率作为上线一票否决项，宁误报不漏报

模型可用性与时延　 DeepSeek 服务波动或慢响应会影响体验，对策是接口超时与重试、流式输出降低等待感、模型不可用时降级为兜底提示而非裸奔报错

患者描述模糊或失真　家属代办、夸大、二手转述会导致信息失真，对策是结构化追问补全关键维度、信息不足时主动兜底、免责声明明确建议以医生面诊为准

隐私合规　对话可能涉及敏感健康信息，对策是匿名 session、不采集身份信息、最小必要处理、留存与脱敏规则单独约定

## 版本路线

V1 MVP（本 PRD 范围）　结构化问诊对话、急诊识别与阻断、混合检索、科室推荐（主推+备选+依据+就医提示）、知识库构建 pipeline、Web 聊天页、标注测试集与准确率评估，目标是跑通"症状到科室"的完整可用闭环并达到验收门槛

V2 　接入 HIS 实现真实挂号与号源查询、医生推荐与排班、会话持久化与多端同步、用户反馈闭环反哺知识库与测试集

V3 　多医院科室知识扩展、专科与亚专科精细化推荐、语音输入与方言适配、主动健康提示与复诊提醒

```

├── src/
│   ├── core/        配置加载、模型客户端、通用工具

│   ├── agent/       LangGraph 状态机、节点、Prompt 模板
│   └── api/         FastAPI 接口、会话管理、限流日志
├── data/
│   ├── raw/         原始抓取 HTML
│   ├── clean/       清洗后的 Markdown
│   ├── chunks/      切分后的 Chunk JSONL
│   └── vectorstore/ Chroma 向量库（待建）
├── tests/           单元测试、检索评测、端到端测试、标注测试集
├── scripts/         构建知识库、跑评测等可执行脚本
├── config/          配置文件与 Prompt 模板
├── web/             前端聊天页静态资源
├── docs/            PRD、设计文档、标注规范

├── pyproject.toml   依赖与项目元信息
└── README.md        项目说明与运行指引
```

各目录职责单一、可独立测试，知识库构建（crawler、rag 的离线部分）与在线服务（agent、api）清晰分离，前端与后端解耦，测试与评测资产沉淀在 tests 下随项目演进
